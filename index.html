The problems.
The story behind them.

These aren't isolated tech choices — they're a connected engineering journey building a real-time seat availability platform from a server that kept falling over to a system that held through the Eras Tour. Each card leads with the problem it solved.

01
The server was falling over under fan traffic
During major on-sales, a single server would get overwhelmed by concurrent fan requests and go down. Reliability was a guess. We moved to a Kubernetes cluster on AWS EKS with round-robin load balancing so no single machine bore the full weight. We load-tested aggressively before each major on-sale to find the breaking point, and put circuit breakers in place so a traffic spike on the event page couldn't cascade and take down shared upstream services across the platform.
Kubernetes / EKS KEDA Autoscaling Load Testing Circuit Breaking
Deep dive

The problem: A list of event sections was rendered on page load — each item immediately triggering an API call for section imagery and metadata, regardless of whether the fan had ever scrolled there. On a large arena, this meant 200–300 simultaneous origin requests at cold load. It was hammering the origin, inflating CDN costs, and causing measurable render jank on mid-range mobile devices.

The Engineering Challenge

The naive fix — pagination or a "load more" button — would have degraded the UX by requiring the fan to take extra action. The goal was zero wasted requests with zero visible change to the user experience. The solution had to work in a server-side rendered Next.js environment where components mount asynchronously and the list could contain a dynamic number of items.

The Approach

I replaced the eager-fetch pattern with an IntersectionObserver-driven lazy-fetch architecture. Each list row registers an observer on mount. The API call fires only when that row enters the viewport — not before. Rows the fan never reaches never make a network request. The observer is cleaned up after the first intersection to avoid duplicate fetches.

A subtle challenge: the list is virtualized, so rows mount and unmount as the fan scrolls. I had to ensure observer registration was idempotent and that cached responses were reused correctly when a row remounted — avoiding redundant fetches for sections the fan had already scrolled past.

02
Bots were getting free access to live seat inventory — and we had no auth
Automated bots were opening persistent connections and getting a live stream of seat availability data with no authentication. We couldn't reliably track IPs, and auth wasn't a hard requirement in the system yet. We first put a queue in front of the connection path that worked as a rate limiter — too many connections from the same origin in a short window got rejected before reaching the service. That bought time to build the real fix: JWT tokens issued at page load, validated at the ISTIO service mesh layer before the WebSocket upgrade even completes. The application never sees an unauthenticated connection. No changes needed in any individual service.

Deep dive

The problem: The legacy system used HTTP polling — clients periodically asked the server whether seat state had changed. Under a major presale (think: millions of fans simultaneously), polling produced stale data, seat collisions, and failed purchases. The round-trip latency meant a seat could be sold between when you last polled and when you tried to check out. "Eventually consistent" is not acceptable when the data has a price tag.

The Engineering Challenge

The payload problem alone was hard: a large venue has up to 100,000 seats, each with an available/unavailable bit. Sending the full state on every update is wasteful; sending diffs requires the client to maintain and reconcile state. The deserialization problem is also real — parsing binary data on the browser's main thread at high update frequency causes UI jank. And then there's the diffing question: should the server or the client compute what changed?

The Approach

We replaced polling with a push-based architecture over WebSocket. On the backend, a Kafka Streams application consumes raw inventory events, transforms and deduplicates them, and encodes the current seat availability state as a compressed RoaringBitmap — a data structure specifically designed for sparse bit sets, capable of representing 100,000 seat states in a few kilobytes. This eliminates diffing: we just send the full current bitmap on every state change. The client reads it and lights up seats accordingly.

A gRPC StatefulSet service bridges the Kafka layer to the WebSocket delivery tier. For browser deserialization, I chose FlatBuffers as the wire format (zero-copy, no parsing overhead) and implemented the decoding in WebAssembly for near-native speed, offloaded to a Web Worker so decoding never touches the main thread even when thousands of updates arrive simultaneously. I built a typed client SDK around all of this — frontend teams subscribe to seat state as a simple observable; they never interact with the binary protocol, the WebSocket lifecycle, or the compression scheme.

Price and attribute data changes less frequently than seat state. That channel uses a version token over WebSocket — when the client detects a version mismatch, it fires a targeted HTTP refetch. Since each version is immutable and the WebSocket controls all cache invalidation, HTTP responses carry high TTLs and cache well at the CDN.

03
Tracking available seats was too slow — so we flipped it and tracked what's gone
The system kept a running list of every seat that was currently available. Every time one sold, we had to re-derive the full available set from scratch — expensive at high load and increasingly wrong during peak demand. We flipped the model: track what's gone instead. When a seat sells, add it to the unavailable set. When a hold expires, remove it. Available seats are implicitly everything not on that list — no full re-query needed on every change. We backed the list view with an S3 manifest snapshot so the display layer recalculates from a known state, not the entire inventory. The Eras Tour on-sale ran on this model — that was the proof point.
Java S3 / Object Storage Unavailability-First Model Eras Tour scale
Deep dive

The problem: The availability service maintained a positive list — the set of seats that were currently available for display in the list view. Every time inventory changed (a seat sold, a hold expired, a new allotment released), the service had to re-derive the full available set. Under rapid-fire state changes during a high-demand on-sale, this produced expensive re-queries, race conditions, and a list view that visibly lagged real inventory.

The Engineering Challenge

The fundamental issue is a data model mismatch. Tracking availability in a positive-set model couples every read to the entire event inventory — a full re-query on every write. At high event concurrency, this becomes a bottleneck and a correctness hazard. The challenge was finding a representation that made updates cheap while keeping reads correct.

The Approach

I redesigned the model to be unavailability-first: the system now tracks the complement — the set of seats that are no longer available (sold, held, blocked). Availability is implicitly everything that isn't in the complement. This makes writes cheap: a seat sold? Add it to the unavailability delta. A hold expires? Remove it. No full re-query needed.

To support the list view rendering without a full inventory fetch, I introduced an object storage-backed manifest — a snapshot of the current display state serialized to S3. When user input changes (filter applied, price range adjusted) or system state changes (new allotment, hold expiry), the service recalculates only against the delta and the manifest, not the full inventory. This made the service significantly more maintainable: new availability rules could be added as manifest delta transformations without touching the core query path.

The Tradeoff

The unavailability-first model requires careful handling of set complement semantics when the universe (total seat count) changes — for example, when additional inventory is released mid-sale. I built explicit reconciliation logic for these events to prevent the complement from silently producing a stale or incorrect available set.

04
We had no way to know if the new system matched the old one — so we built a comparator
Once unavailability-first was live, we needed more than "is it working?" — we needed to know how close the new system was to the legacy one, seat by seat, at any given moment. Without that, fully cutting over was a leap of faith. We built a Lambda function that ran both systems in parallel for the same event and produced a structured comparison report covering availability state, offer data, price, and seat attributes. This gave us a quantitative gap analysis — we could see exactly where and how often the systems diverged and close those gaps before committing to the new model fully.

Deep dive

The problem: An event page before tickets go on sale (offsale) and after (onsale) are genuinely different products — different CTAs, different data fetches, different structured data for search engines, different CDN caching requirements. The codebase handled this with if (isOnSale) branching scattered across dozens of components. Both states were perpetually fragile: a fix for one broke the other.

The Engineering Challenge

The core issue is that sale state is a routing concern, not a rendering concern. When conditional logic lives inside components, you've already made the wrong architectural decision — you've coupled page shape to component state rather than to the URL contract. The challenge was extracting that decision upward without a massive component tree rewrite.

The Approach

I introduced context-path routing at the Next.js router layer — onsale and offsale states are given distinct URL contexts. SSR now renders the correct page shape from the start: on an offsale path, the server knows immediately which data to fetch, which structured data to emit, and which component variants to activate. The component tree remains shared (no forking), but each context receives a clean typed contract from the router rather than inferring state from scattered flags.

The CDN benefit is significant: Fastly can now cache onsale and offsale as distinct response variants with different TTLs — offsale pages can be cached aggressively (the inventory model doesn't change), while onsale pages carry short TTLs or bypass cache selectively. Previously, Ticketmaster had to use the same cache policy for both states, which forced a conservative short TTL even when most traffic was hitting offsale events where long caching was safe.

The Tradeoff

Adding a routing dimension means managing sale-state transitions — when an event goes onsale, the correct path changes and the fan's current URL may become stale. I implemented router-level redirect logic to handle this transition cleanly, including preserving query parameters (selected section, price filter, accessibility flags) across the redirect.

05
We were finding out the system broke by watching Twitter
There was no structured way to know what a fan actually experienced on the page during an on-sale. If something went wrong — slow seat data, a disconnected WebSocket, a list view out of sync with the seatmap — the first signal was often social media. We instrumented the client to track what the fan saw: when seats arrived, how long the connection took, when it dropped, whether the list matched the seatmap. Those events flow to Kafka, fan out to Splunk for real-time alerting, and land in a database for post-event analysis. Now we know what happened on the client before anyone tweets about it.

Deep dive

The problem: Generic event searches — "[artist] [city] tickets" — were landing pages between positions 5–12, frequently on page 2, with no rich snippet eligibility. Search engines saw rendered HTML but no machine-readable event data: no start time, no ticket price range, no venue, no offer status. Google couldn't generate event boxes, rich cards, or Knowledge Panel entries without structured data.

The Engineering Challenge

The first instinct is to inject JSON-LD via a client-side script tag after hydration. This is wrong. Googlebot does fetch JavaScript, but structured data in client-injected scripts is processed less reliably than data in the initial HTML response. The constraint was: structured data must be in the SSR HTML, fully formed, before the response leaves the server.

The second challenge: structured data in Next.js SSR can drift. Server renders the page with the correct structured data, hydration runs, client-side state updates, and a React re-render silently overwrites the structured data injected during SSR. The page looks correct to the user but the data Google indexed is stale or missing.

The Approach

I added JSON-LD Event schema (including MusicEvent, SportsEvent, Offer, venue, and artist entities) directly into getServerSideProps and rendered into a <script type="application/ld+json"> tag in the page <head> at SSR time. The schema is built from the same data contract used to render the page — no separate fetch, no duplication.

To catch hydration drift, I built post-hydration DOM verification hooks that re-read the injected structured data after client-side hydration completes and compare it against the expected canonical values. Drift triggers an alert and a targeted correction, ensuring what Google indexes matches what the server rendered.

For discoverability, I wired a sitemap generator directly to the Next.js router. Instead of a static XML file that lagged event creation, the sitemap is generated dynamically on a schedule from the same route definitions the app uses — ensuring every live event URL is crawlable with the correct lastmod and priority signals.

06
The seatmap and the list view needed opposite models — with a kill switch if either broke
The seatmap (visual seat picker) and the list view (scrollable seat list) have fundamentally different display logic. The seatmap renders from a live bitmap — it needs to show what's there and light it up, availability-first. The list view renders from confirmed gone seats — it hides rows, unavailability-first. We built and shipped both models together, with each surface driven by its own logic, and put both behind a feature flag. If either surface shows unexpected behavior in production, the flag flips and that surface rolls back instantly — no deploy, no incident. This also meant we could verify them independently against the shadow comparator before committing to either.

Deep dive

The problem: The page runs two parallel data channels. A WebSocket push stream delivers seat availability state at sub-second latency — authoritative during an active sale. An HTTP API delivers richer per-seat metadata (price tier, attributes, display labels) with responses cached at Fastly with high TTLs for cost efficiency. When a seat sells, the push stream fires immediately. But the cached HTTP response for that seat's metadata hasn't expired yet. Result: the list view shows a seat the fan cannot buy.

The Engineering Challenge

This is a classic read-your-writes consistency problem across heterogeneous data sources with different latency and staleness characteristics. You can't make the HTTP cache expire faster without losing the cost savings that justify using a CDN. You can't ignore the push stream without re-introducing seat collisions. The two sources serve different concerns — availability state vs. availability metadata — and conflating them is the root cause of the bug.

The Approach

The fix is a strict separation of concerns enforced in the client SDK: the push stream is the sole authority for seat availability state; the HTTP channel is the sole authority for seat metadata. These are now distinct concerns that never overwrite each other.

The SDK maintains a local availability overlay — an in-memory truth table of seat states driven exclusively by the push stream. When a push event marks a seat as unavailable, the overlay is updated immediately and the list view suppresses that row. If a stale HTTP cache response subsequently arrives carrying "available" metadata for the same seat, the overlay intercepts it and prevents re-surfacing. The seat stays suppressed until the push stream explicitly clears it.

Cache invalidation signals flow through the same WebSocket channel as seat state: when the server rotates a price/metadata version, it sends a version token. The client detects the mismatch and fires a targeted HTTP refetch — bypassing the CDN cache for that specific resource. This keeps cache invalidation event-driven rather than TTL-driven, without requiring a full cache flush.

The Insight

The underlying principle: don't reconcile across authority boundaries at the leaf layer. Ghost seats appeared because the component layer was trying to merge two sources of truth. Moving that decision up to the SDK layer — with explicit rules about which source wins for which concern — eliminated the entire bug class without adding any latency to the critical path.

The problem: WebSocket connections are long-lived. Once established, they stream real-time inventory state continuously. An unauthenticated connection receives a perpetual, free firehose of seat availability data — useful for automated scalping bots that want to know the moment inventory appears. Unlike HTTP endpoints where per-request auth is straightforward, WebSocket auth requires deliberate design: the HTTP upgrade handshake is the only natural auth checkpoint.

The Engineering Challenge

Application-layer auth in a WebSocket handler has a flaw: the connection is already established when the app gets involved. A bot can open a connection and start receiving data before any auth check fires. You need auth enforcement before the upgrade. Additionally, standard JWT validation at the app layer means every service must implement it — creating an inconsistent surface area and increasing the blast radius of any implementation bug.

The Approach

I moved JWT enforcement to the ISTIO service mesh layer using ISTIO's RequestAuthentication and AuthorizationPolicy resources. The browser acquires a short-lived JWT at page load via a standard auth flow. This token is included in the WebSocket upgrade request headers. ISTIO's Envoy sidecar validates the JWT before the upgrade handshake completes — a rejected token means no connection, full stop, at the infrastructure layer. The application never sees an unauthenticated socket.

JWT claims include a session binding that ties the connection to the fan's current page session. This prevents a valid token obtained by one session from being redistributed to a bot farm — each token is scoped to a single session fingerprint and expires after a short window. Token refresh is handled transparently by the client SDK.

Enforcement at the mesh layer means zero application code changes across the multiple services that back the WebSocket infrastructure — auth is a deployment concern, not a code concern. Prometheus metrics on failed upgrade attempts feed anomaly detection for unusual connection patterns.

08
The CDN was protecting the server but serving fans the wrong data
We cached event page responses with long TTLs so the origin could survive a million fans hitting simultaneously. But when pricing or event details changed, fans were still seeing the cached stale version. A full cache wipe would expose the origin to the same traffic it was supposed to absorb. We solved it by tagging every cached response with surrogate keys — structured identifiers tied to event ID, pricing version, and sale state. When something changes, a targeted purge hits only those responses, never the whole cache. We also built a pre-warm pipeline using AWS Step Functions that fills the CDN with fresh data minutes before a sale opens, so the first wave of fan traffic hits warm cache rather than a cold origin under peak load.
Fastly VCL Surrogate Key Purging Stale-While-Revalidate AWS Step Functions
Deep dive

The problem: High cache TTLs protect your origin from the first wave of an on-sale. But when pricing, event attributes, or sale state change, fans on cached responses see stale data. Purging everything is expensive and can expose the origin to thundering herd. Purging nothing means correctness failures. The challenge is surgical cache invalidation at CDN scale without operational fragility.

The Engineering Challenge

Fastly VCL (Varnish Configuration Language) runs at the network edge — a restricted, stateless language with no access to your application or database. Cache invalidation logic must be expressed purely as: key matching, response header rules, and purge API calls. You can't ask "did this response become stale?" — you have to design staleness out of the caching model upfront.

The Approach

Surrogate key-based purging is the foundation. Every cached response is tagged at origin with structured Surrogate-Key headers composed of meaningful dimensions: event ID, venue, pricing version, sale state. When something changes, a targeted purge fires against exactly those keys — evicting only the affected responses, never the whole cache. This required disciplined tagging at the origin layer and a purge orchestration service that knew which keys to invalidate for each type of state change.

Stale-while-revalidate (configured in VCL) ensures fans always receive a response even during purge windows — the edge serves the stale response while simultaneously revalidating in the background, preventing a latency spike during high-traffic moments when a purge triggers.

For on-sale openings — the highest-traffic moment — I built a pre-warm pipeline using AWS Step Functions. Minutes before a sale opens, the pipeline proactively fetches canonical event URLs through the CDN, populating Fastly's cache with fresh responses before the fan wave hits. The first million requests land on warm cache rather than hammering a cold origin.

The Iteration

Each major on-sale event revealed an edge case the VCL rules didn't cover — a cache key collision, a TTL that was too long for a specific response type, a surrogate key that didn't propagate correctly through Fastly's shielding layer. The current strategy is the result of iterative refinement across multiple high-profile events, each one teaching something about where the model breaks under real traffic distribution.

09
Turning on a feature flag was adding a round-trip to every fan's checkout path
Standard A/B test and feature flag systems make a network call to a remote service to decide which variant a user gets. During an on-sale at peak load, that round-trip is visible latency on the path to checkout — and when a flag changes, active sessions have to reload the page to see it. We built a Node.js service that keeps a local copy of all flag rules and evaluates them in-process — no round-trip, no added latency. A Java backend streams all flag decisions through Kafka for analytics. When a product team flips a flag in production, the change propagates live to all connected sessions over the existing WebSocket — every fan sees the update without reloading the page.
Node.js local evaluation Java / gRPC Kafka WebSocket live delivery Optimizely / Kameleoon
Deep dive

The problem: Standard feature flag evaluation makes a round-trip to a remote flag service on each request or page load. At Ticketmaster's scale — millions of concurrent sessions, many during time-sensitive on-sales — that round-trip adds meaningful latency to the critical purchase path. Additionally, when a flag changes, currently active sessions don't see the change until their next full page load. That's a slow, blunt instrument for a real-time platform.

The Engineering Challenge

Flag evaluation must be zero-round-trip-latency on the hot path. Flag updates must propagate in real time to active sessions without a reload. The system must support multiple flag providers (different teams had contracted with different vendors) interchangeably. And the full assignment event stream must flow to analytics for experiment evaluation — you can't measure an A/B test if you don't know who got which variant.

The Approach

I built a two-layer architecture. The first layer is a Node.js edge service that integrates with both Optimizely and Kameleoon (used interchangeably based on each team's contract). It maintains a local copy of all flag and experiment rulesets, synced continuously from each provider's SDK. Flag evaluation happens in-process — microsecond latency, no external round-trip. The service is stateless and horizontally scalable.

The second layer is a Java backend service that processes experiment decisions over gRPC, persists assignment state in RocksDB for fast local lookups and durability across restarts, and streams all assignment events to Kafka. From Kafka, the stream fans out to a Splunk pipeline (for real-time alerting) and a database (for offline experiment analysis).

Flag delivery to active browser sessions happens over the existing WebSocket infrastructure. When a flag or variant changes in production, the update propagates through the backend service and arrives at all connected clients over WebSocket — no reload, no polling. The client SDK receives the updated flag state and re-renders the relevant components. This turns feature flag delivery into a real-time operation with the same latency characteristics as seat state updates.
